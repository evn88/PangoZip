# Автоматический выпуск DMG

Workflow `.github/workflows/release.yml` запускается при отправке нового тега вида `v0.7.0`. Проверяет версии трёх пакетов, форматирование, shell-сценарии, автоматизацию выпуска и Swift-тесты. Затем собирает arm64-приложение на `macos-26`, проверяет подпись, упаковывает и проверяет DMG, формирует SHA-256 и описание на **ENG/RUS**.

Отдельное задание получает только проверенные артефакты и права `contents: write`. Оно повторно проверяет SHA-256 и соответствие удалённого тега собранному коммиту, создаёт черновик релиза, загружает DMG, `.sha256` и подписанный `appcast.xml`, проверяет размеры и серверные хеши и только после этого публикует обычный релиз с явной отметкой **Latest**. Описание включает установку, архитектуру, ограничения подписи, проверку суммы и лицензии 7-Zip.

## Новый релиз

1. Согласованно обновите `CFBundleShortVersionString` в `Resources/Info.plist`, `Resources/WorkerInfo.plist` и `FinderExtension/Info.plist`. Например, для `v0.7.0` во всех трёх должно быть `0.7.0`. Также увеличьте и согласуйте `CFBundleVersion`.
2. При желании добавьте `docs/releases/v0.7.0.json` с массивами строк `en` и `ru`. Пример структуры — `docs/releases/v0.6.0.json`. Списки попадут в соответствующие разделы изменений. Если файла нет, описание содержит двуязычную ссылку на историю исходников, без выдуманных изменений.
3. Закоммитьте и отправьте исходники, затем создайте и отправьте тег:

   ```sh
   python3 scripts/release_metadata.py validate v0.7.0
   git tag -a v0.7.0 -m 'PangoZip 0.7.0'
   git push origin v0.7.0
   ```

4. Дождитесь успешного workflow **Release DMG** в Actions. Готовые файлы появятся в Releases, новый релиз станет Latest на главной странице репозитория.

Используйте увеличивающиеся окончательные версии `vMAJOR.MINOR.PATCH`. Суффиксы `-beta`, `-rc` и `+metadata` не поддерживаются: GitHub не позволяет назначать prerelease как Latest. Старый номер, несовпадающие версии, изменённый тег и существующий опубликованный релиз приводят к остановке. Опубликованные файлы никогда не перезаписываются. При сбое загрузки можно повторить тот же workflow: он восстановит черновик, заменив только два ожидаемых файла. Для нового кода нужен новый тег.

Теги нужно отправлять обычным Git push от пользователя или подходящим GitHub App/PAT. События, созданные другим workflow через его `GITHUB_TOKEN`, обычно не запускают новый workflow. Если Actions или запись релизов запрещены политикой репозитория/организации, сначала разрешите их в настройках GitHub. Личный PAT для обычного сценария выпуска не нужен.

## Проверка без публикации

Actions → **Release DMG** → **Run workflow**: выберите ветку и версию, совпадающую с её исходниками. Например, для текущих исходников `v0.6.0`. Ручной запуск проверяет и собирает файлы, сохраняет `release-bundle` на 14 дней, но **не создаёт и не меняет релиз**. Это позволяет проверить автоматизацию без искусственного публичного тега.

## Подпись Apple

По умолчанию используется ad hoc подпись без обращения к Apple. В обеих языковых версиях описания есть предупреждение об отсутствии Developer ID/нотариализации и возможной блокировке Gatekeeper. Отметка Latest означает последний релиз, а не проверку Apple.

После получения сертификата настройте Settings → Secrets and variables → Actions:

| Secret | Значение |
|---|---|
| `PANGOZIP_CERTIFICATE_BASE64` | Base64 экспортированного `.p12` с Developer ID Application и приватным ключом |
| `PANGOZIP_CERTIFICATE_PASSWORD` | Непустой пароль защиты `.p12` |
| `PANGOZIP_SIGNING_IDENTITY` | Полное имя `Developer ID Application: YOUR NAME (TEAMID)` |
| `PANGOZIP_APPLE_ID` | Apple Account для нотариализации |
| `PANGOZIP_APPLE_TEAM_ID` | Team ID |
| `PANGOZIP_APPLE_APP_PASSWORD` | Пароль приложения Apple, не основной пароль аккаунта |

Создайте repository variable **`PANGOZIP_NOTARIZE=true`**. До её включения сборка остаётся ad hoc, даже если отдельные секреты уже добавлены. После включения отсутствие любого секрета, ошибка подписи или отказ Apple останавливают выпуск: автоматического отката к ad hoc нет.

Сертификат импортируется во временный Keychain выделенного GitHub-hosted runner. Учётные данные нотариализации сохраняются там же в профиль `PangoZip-CI`; `notarize-release.sh` использует этот профиль. Приватные материалы удаляются в завершающем шаге, в артефакты не попадают. Сценарий `ci-signing.sh` предназначен для одноразовых GitHub-hosted runner, не для self-hosted машин с пользовательским Keychain.

Для передачи Base64 в GitHub можно использовать локально `base64 -i DeveloperID.p12 | gh secret set PANGOZIP_CERTIFICATE_BASE64 --repo evn88/PangoZip`; остальные значения безопаснее вводить через защищённые поля GitHub. Не коммитьте и не присылайте секреты в чат. Подробности локальной подписи: [notarization.md](notarization.md).

Нотариализованный режим сохраняет подтверждения у приложения и DMG; описание ENG/RUS обновляется на фактический принятый статус. При ошибке доступные журналы Apple сохраняются отдельным артефактом `notarization-reports` на 7 дней. До добавления сертификата реальная нотариализация в GitHub не проверена.
