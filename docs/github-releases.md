# Автоматический выпуск из main

После каждого изменения `main` workflow **Release from main** (`.github/workflows/release.yml`) сам готовит следующую версию, запускает проверки, собирает arm64-приложение и DMG, подписывает ленту автообновлений и публикует GitHub Release с отметкой **Latest**. Для обычного выпуска достаточно влить проверенный pull request в `main`. Ручное изменение версий, создание тега и загрузка файлов не нужны.

## Версия и состав релиза

По умолчанию увеличивается patch: `0.7.0 → 0.7.1 → 0.7.2`. `CFBundleVersion` увеличивается независимо и остаётся выше номеров сборок существующих окончательных тегов. Все четыре пакета — приложение, worker, Finder Sync и Quick Look — получают одну версию и номер сборки. README в теге и описание релиза обновляются автоматически. Версии в main служат исходной базой; фактическая версия сборки записана в релизном теге. Пользовательский список берётся из `docs/releases/vX.Y.Z.json`; без него используется нейтральное «Техническое обновление приложения», без названий коммитов и неподтверждённых обещаний исправлений.

Если нужен minor или major, заранее задайте новую согласованную `CFBundleShortVersionString` во всех четырёх `Info.plist`. Версия, которая выше всех существующих окончательных тегов, будет сохранена; номер сборки workflow повысит сам. Подготовленный вручную `docs/releases/vX.Y.Z.json` с массивами `en` и `ru` используется вместо стандартного списка. Можно добавить все 14 языков приложения, как в `docs/releases/v0.7.2.json`; пункты должны быть короткими строками обычного текста. Prerelease и теги с metadata в нумерации обычных релизов не участвуют.

## Порядок и защита от гонок

1. Checkout привязан к точному SHA события `main`. Если этот SHA уже устарел, запуск завершается без выпуска: более новый ожидающий запуск включает накопленные изменения.
2. `scripts/main_release.py prepare` создаёт локальный коммит версии. На этом этапе удалённые `main` и теги не меняются.
3. Проверяются версии компонентов, Swift Format, shell-сценарии, Python-тесты автоматизации и Swift-тесты. Затем собираются приложение, подпись и DMG; создаются SHA-256 и подписанный `appcast.xml`. Проверенный комплект сохраняется как артефакт на 14 дней.
4. После проверок публикуется только тег коммита версии. В main служебный коммит не отправляется: защита «изменения через pull request» остаётся включённой. Если main продвинулся до последней проверки, выпуск пропускается. Если main изменился уже между проверкой и push тега, тег содержит проверенный снимок предыдущего main, а следующий запуск выпускает новую версию. Force push не используется.
5. Задание публикации проверяет соответствие тега коммиту, размеры и SHA-256 трёх файлов, загружает их в черновик и лишь после проверки переводит релиз в опубликованный Latest. DMG, `.sha256` и `appcast.xml` всегда относятся к одному коммиту.

Concurrency-группа сериализует выпуски. Во время длинной сборки GitHub сохраняет последний ожидающий запуск; несколько быстрых коммитов могут попасть в один следующий релиз. Тег отправляется штатным `GITHUB_TOKEN`; main не меняется, поэтому рекурсивного повышения версии нет. Проверки pull request выполняются отдельным workflow **Swift**, без прав публикации.

## Повтор после сбоя

В Actions откройте неудачный **Release from main** и выберите **Re-run failed jobs**. Если требуется повторить весь сценарий, можно использовать **Re-run all jobs** либо **Run workflow** на ветке `main`. Ручной запуск тоже публикует релиз; запуск с другой ветки или тега пропускается.

- Если сборка упала до push, удалённые refs не меняются.
- Если тег уже отправлен, повтор находит исходный SHA в сообщении релизного коммита и использует тот же тег, коммит и номер версии.
- Незаконченный черновик восстанавливается с проверенными файлами.
- Уже опубликованный релиз не заменяется. Повтор задания публикации допускается только при полном совпадении артефактов; он не меняет Latest задним числом.
- Повтор для уже опубликованного коммита завершается без нового релиза. Новое изменение в `main` запускает следующую версию.

Нужен секрет `PANGOZIP_SPARKLE_PRIVATE_KEY`, соответствующий `SUPublicEDKey` приложения. PAT не нужен. Workflow явно запрашивает `contents: write` только для доверенных заданий на `main`. Защита main может требовать pull request: workflow не пишет в эту ветку и не обходит branch protection. Правила тегов должны разрешать GITHUB_TOKEN создавать релизные теги.

Если правила main требуют CodeQL, включите **Settings → Code security → CodeQL analysis → Default setup** для Swift, Python и GitHub Actions. Сначала должен успешно завершиться первоначальный анализ main, затем анализ pull request. Одно правило защиты без настроенного анализа блокирует слияние сообщением «Waiting for Code Scanning results». Default setup хранится в настройках GitHub; отдельного CodeQL workflow в репозитории нет.

Локальные тесты сценария используют временные bare-репозитории и проверяют гонки, повторные запуски, отсутствие одиночного тега при отказе push и согласованность версий:

```sh
python3 -m unittest discover -s scripts/tests -p 'test_*.py'
```

## Подпись Apple

По умолчанию используется ad hoc подпись без обращения к Apple. В обеих языковых версиях описания есть предупреждение об отсутствии Developer ID/нотариализации и возможной блокировке Gatekeeper. Отметка Latest означает последний релиз, а не проверку Apple.

После получения сертификата настройте Settings → Secrets and variables → Actions:

| Secret | Значение |
|---|---|
| `PANGOZIP_CERTIFICATE_BASE64` | Base64 экспортированного `.p12` с Developer ID Application и приватным ключом |
| `PANGOZIP_CERTIFICATE_PASSWORD` | Непустой пароль защиты `.p12` |
| `PANGOZIP_SIGNING_IDENTITY` | Полное имя `Developer ID Application: YOUR NAME (TEAMID)` |
| `PANGOZIP_APPLE_ID` | Apple Account для нотариализации |
| `PANGOZIP_APPLE_TEAM_ID` | Team ID |
| `PANGOZIP_APPLE_APP_PASSWORD` | Пароль приложения Apple, не основной пароль аккаунта |

Создайте repository variable **`PANGOZIP_NOTARIZE=true`**. До её включения сборка остаётся ad hoc, даже если отдельные секреты уже добавлены. После включения отсутствие любого секрета, ошибка подписи или отказ Apple останавливают выпуск: автоматического отката к ad hoc нет.

Сертификат импортируется во временный Keychain выделенного GitHub-hosted runner. Учётные данные нотариализации сохраняются там же в профиль `PangoZip-CI`; `notarize-release.sh` использует этот профиль. Приватные материалы удаляются в завершающем шаге, в артефакты не попадают. Сценарий `ci-signing.sh` предназначен для одноразовых GitHub-hosted runner, не для self-hosted машин с пользовательским Keychain.

Для передачи Base64 в GitHub можно использовать локально `base64 -i DeveloperID.p12 | gh secret set PANGOZIP_CERTIFICATE_BASE64 --repo evn88/PangoZip`; остальные значения безопаснее вводить через защищённые поля GitHub. Не коммитьте и не присылайте секреты в чат. Подробности локальной подписи: [notarization.md](notarization.md).

Нотариализованный режим сохраняет подтверждения у приложения и DMG; описание ENG/RUS обновляется на фактический принятый статус. При ошибке доступные журналы Apple сохраняются отдельным артефактом `notarization-reports` на 7 дней. До добавления сертификата реальная нотариализация в GitHub не проверена.
